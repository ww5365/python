

## vLLM-Ascend的图执行优化

### CANN侧的(GE)图编译优化和vLLM-Ascend的图执行优化区别

| | **CANN GE（编译器）** | **vLLM-Ascend ACLGraphWrapper（播放器）** |
|---|---|---|
| **发生时机** | 编译期（`torch.compile` 触发） | 运行期（每次 forward 调用） |
| **做什么** | 改写计算图结构（如 MatMul+Add → GEMM），生成优化后的执行序列 | 把已生成的执行序列“录制”为 `NPUGraph`，后续直接 `replay()` |
| **代码体现** | `PatternFusionPass` 的 `patterns()` / `replacement` 定义 | `ACLGraphWrapper.forward` 中的缓存查找与 `aclgraph.replay()` |
| **解决的开销** | 算子数量、Kernel 启动次数、内存读写 | Python 调度、主机与设备交互、逐算子 launch |





### 图优化的示例

用一个具体的 **MLP 层**（`Y = GELU(X @ W1 + b1) @ W2 + b2`）为例，分两个层面画图对比：**GE 编译优化改变“图长什么样”**，**ACLGraph 重放改变“图怎么被执行”**。

#### 1、GE 编译优化：图结构从“5 个算子串行”变成“2 个融合算子”



##### 优化前：原始计算图（逐算子执行）

```
         X
         │
    ┌────▼────┐
    │ MatMul  │  ← 算子①  X @ W1
    │  (W1)   │
    └────┬────┘
         │ T1  ──→ 写入 HBM
    ┌────▼────┐
    │   Add   │  ← 算子②  T1 + b1
    │  (b1)   │
    └────┬────┘
         │ T2  ──→ 写入 HBM
    ┌────▼────┐
    │  GELU   │  ← 算子③  GELU(T2)
    └────┬────┘
         │ T3  ──→ 写入 HBM
    ┌────▼────┐
    │ MatMul  │  ← 算子④  T3 @ W2
    │  (W2)   │
    └────┬────┘
         │ T4  ──→ 写入 HBM
    ┌────▼────┐
    │   Add   │  ← 算子⑤  T4 + b2
    │  (b2)   │
    └────┬────┘
         │
         Y
```

**代价**：5 次 Kernel launch + 4 次中间 Tensor 写入 HBM + 4 次从 HBM 读出 → **9 次 HBM 往返**。

##### 优化后：GE 编译后的融合计算图

GE 的 PatternFusionPass 在编译期识别出 `MatMul+Add+GELU` 和 `MatMul+Add` 两个可融合子图，将它们分别替换为单一融合算子：

```
         X
         │
    ┌────▼──────────────────┐
    │  FusedMatMulAddGELU   │  ← 融合算子①  (X @ W1 + b1) → GELU
    │      (W1, b1)         │
    └────┬──────────────────┘
         │ T1' ──→ 写入 HBM（只有一个中间 Tensor）
    ┌────▼──────────────────┐
    │    FusedMatMulAdd     │  ← 融合算子②  T1' @ W2 + b2
    │      (W2, b2)         │
    └────┬──────────────────┘
         │
         Y
```

**代价**：2 次 Kernel launch + 1 次中间 Tensor 写入 HBM + 1 次读出 → **仅 2 次 HBM 往返**。

**融合带来的收益**：算子数 5→2，中间 Tensor 4→1，Kernel launch 5→2，HBM 读写 9→2。融合算子在 NPU 内部连续执行，中间结果留在片上缓存（如 L1/L0），不落地到 HBM。

#### 2、ACLGraph 重放：执行方式从“逐算子调度”变成“整图一次播放”

图结构优化后，不管图里有 2 个还是 200 个算子，运行时仍然需要有人**逐个把算子“发射”到 NPU 上**。这一步由 vLLM-Ascend 的 `ACLGraphWrapper` 接管。

##### 没有 ACLGraph：每次 forward 都逐算子调度

```
Host (Python/CPU)                          Device (NPU)
──────────────────                         ────────────
  vLLM 调度器调 model(...)
       │
       ├─ 调 融合算子① ───────────────→  launch kernel①
       │  等待完成 ←───────────────────  kernel① 执行
       │
       ├─ 调 融合算子② ───────────────→  launch kernel②
       │  等待完成 ←───────────────────  kernel② 执行
       │
       └─ 返回输出
```

每个算子都有一次 **Host→Device 的 Kernel launch** 和一次 **同步/等待**。对于大模型一层有几十上百个算子，这种逐算子往返的**主机侧开销**会累积成可观的延迟。

##### 有 ACLGraph：捕获一次，后续整图重放

```
第一次 forward（捕获阶段）：
Host                                      Device
────                                      ──────
  ACLGraphWrapper.forward()
       │
       ├─ 执行一遍完整序列 ──────────→  kernel① → kernel② → ...
       ├─ 同时“录制”为 NPUGraph
       └─ 缓存 entry（key = BatchDescriptor）

后续每次 forward（重放阶段）：
Host                                      Device
────                                      ──────
  ACLGraphWrapper.forward()
       │
       ├─ 命中缓存
       └─ aclgraph.replay() ──────────→  ┌─────────────────────┐
                                          │ kernel① → kernel②   │
                                          │ （整段连续执行，     │
                                          │  无逐算子 host 往返）│
                                          └─────────────────────┘
       ←───────────────────────────────  返回输出
```

**关键区别**：重放阶段，Host 只发起**一次** `replay()` 调用，整个执行序列在设备侧连续跑完，**消除了每个算子各自的 launch 与同步开销**。这就是 vLLM 静态图执行模式在昇腾上的落地方式。

#### 3、两层优化叠加后的整体效果

把两个层面画在同一张对比图里：

```
┌─────────────────────────────────────────────────────────────────┐
│                    优化前                                        │
├─────────────────────────────────────────────────────────────────┤
│  图结构：  MatMul → Add → GELU → MatMul → Add   (5 个算子)      │
│           中间 Tensor T1~T4 全部写回 HBM                        │
│                                                                 │
│  执行方式：Host 逐算子 launch，每个算子一次 host-device 往返     │
│                                                                 │
│  总开销： 5 次 launch + 9 次 HBM 往返 + 5 次 host 同步          │
└─────────────────────────────────────────────────────────────────┘
                              ↓
┌─────────────────────────────────────────────────────────────────┐
│                    优化后                                        │
├─────────────────────────────────────────────────────────────────┤
│  图结构（GE 编译期）：                                          │
│    FusedMatMulAddGELU → FusedMatMulAdd          (2 个融合算子)  │
│    中间 Tensor 仅 1 个，且可留在片上缓存                        │
│                                                                 │
│  执行方式（ACLGraph 运行期）：                                  │
│    首次捕获 → 后续 replay()，整段序列设备侧连续执行             │
│                                                                 │
│  总开销： 2 次 launch（首次）/ 1 次 replay（后续）              │
│           + 2 次 HBM 往返 + 1 次 host 交互                      │
└─────────────────────────────────────────────────────────────────┘
```

**直观感受**：
- **GE 做的事**：把“5 个独立小任务”合并成“2 个大任务”，减少任务数量和中间数据的搬运。
- **ACLGraph 做的事**：把这“2 个大任务”的完整执行过程录下来，之后每次直接“一键播放”，不再逐个任务去指挥。

两者叠加，既让**每个任务本身更高效**（融合、少搬数据），又让**任务之间的调度开销几乎归零**（整图重放）。这就是图执行优化在编译期与运行期两个层面协同带来的收益。

> 思考：ACLGraph：捕获一次后续整图重放，主要收益点？消除了重放阶段 Host 侧逐算子的 Python 调度、Kernel launch 下发、host-device 同步和动态内存分配等一整串开销，让设备侧执行序列以一次调用连续跑完
